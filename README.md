# 饭饭 · 今天吃啥

一个"今天吃什么"的智能体 Demo：自己在保定市，按人均预算档位选餐，AI 读你的口味画像、联网搜真实店铺，最后**配成一桌菜**（一荤一素＋主食，可加汤和饮品），而不是只推荐一道菜。

> 用手机浏览器打开 `index.html` 就能用，单文件、纯前端、不需要服务器。

## 功能

**三步选餐**

1. 选预算档位（按金额界定）：🥣 小饭 ≤¥25 ｜ 🍱 中饭 ¥26-60 ｜ 🍣 吃好饭 ¥61-200，还有一根预算上限滑杆
2. 选食物类型：🍚 吃饭 ｜ 🍜 吃面 ｜ 🍢 其他
3. 说"今天想吃什么"：**标签跟着第 2 步的类型变**——
   - 选 🍚 吃饭 → 问配什么菜系：川菜／粤菜／湘菜／鲁菜／苏浙菜／闽菜／徽菜／家常菜／日式／韩式／东南亚／西北／健康轻食
   - 选 🍜 吃面 → 问面怎么做：汤面／干拌面／炒面／凉面／米线·粉／馄饨水饺／拉面·刀削／意面
   - 选 🍢 其他 → 问什么吃法：火锅／麻辣烫·串串／烧烤／烤肉／炸物快乐／汉堡快餐／披萨／日式料理／甜品饮品／特色小吃／保定本地／轻食沙拉
   或者直接写一句话（例如"想吃点辣的、有汤的"），再**选位置**、选外卖或堂食

**选位置（不用手打地址）**

- 📍 **定位我**：调用浏览器 GPS，再走高德逆地理编码翻译成"河北省保定市莲池区…"。定位到的城市和你选的城市不一样时**自动切换城市**；
  如果那个城市不在城市表里，会**现场加一项**（auto- 开头），所以在任何城市都能用
- 🔍 **选地点**：展开面板后留空就列"离你最近的 25 个地点"（商圈/小区/商场/学校/地铁，按距离排序），
  或者搜关键词（"万博广场""河北大学"）再点一个
- 定位或选点之后会记住**精确坐标**，之后算距离直接用经纬度、不再做地理编码（更准也更快）；
  手动改地址会自动作废那个坐标，避免用错位置
- 浏览器不给定位（比如微信里有时会拦、或你拒绝了权限）时，会提示改用「选地点」或手动填
- 这一步只用高德**"Web服务"Key**，不需要另外申请 JS API Key，页面也不引入任何外部脚本（仍然可以离线打开）

> 换类型时，上一类里勾过、这一类别没有的标签会自动清掉（比如「其他」里勾的"火锅"切到「吃饭」会被取消），
> 避免看不见的标签偷偷影响结果。标签体检见「我的 › 开发者面板 › 今日想吃标签体检」。

**城市切换**

首页地址上方有城市下拉框，目前支持 **保定市 / 北京市 / 福州市**，选择会记在本机。

- **店铺全部联网实时检索**：高德地图优先，没配 Key 时退回 OpenStreetMap。应用**不再内置任何示例饭店**，所以没网、没 Key 时不会拿假店名糊弄你（会明确告诉你"这次没搜到饭店"）
- **所有城市一视同仁**：都只能联网搜店。切换城市只决定"搜哪个城市"（adcode / 中心坐标 / 地标）

加新城市：在 `index.html` 的 `CITIES` 表里加一项（城市名、adcode、市中心坐标、地标快捷地址、商圈关键词），`offline` 决定这个城市有没有离线兜底库。

**一桌菜组合推荐**

菜品带角色标签（一人食 / 荤主菜 / 素菜凉菜 / 主食 / 汤 / 饮品），按档位自动配：

- 中饭 = 主菜 ＋ 主食（预算宽裕再加素菜、饮品）
- 吃好饭 = 主菜 ＋ 素菜 ＋ 主食（再加汤和饮品）
- 如果主菜本身是盖饭或面（自带主食），就只补个小菜，不会配出"面条＋米饭"
- 每桌的每个位置（主菜/一人食/素菜/汤/主食/饮品）都遵守同一条"口径统一"的规则：先在第 2 步选的类别（吃饭/吃面/其他）里挑，这个类别里确实没有（或者都超预算）才放开到这家店的全量菜单。以前只有主食位做类别过滤，于是"小饭"档（¥25 上限、库里几乎没有 ≤¥25 的整份荤菜）主菜位填不上时，会退到全库分最高的一人食（往往是面），再配上米饭 → 出现"成都担担面＋米饭"
- 硬约束：**整桌菜必须是同一家店能一次点齐的**，人均落在档位区间内

**懂你说的话**

- "想吃泰餐" → 跨类别找到泰国餐厅（哪怕你选的是"其他"，泰餐其实是粉和饭）
- "想吃本地特色" → 优先保定驴肉火烧、牛肉罩饼、李鸿章烩菜
- "想喝奶茶" → 甜品饮品当主角，配珍珠奶茶＋冰淇淋

**联网搜真实店铺（2026-09 改成"店为先"）**

以前是「先定一道菜 → 拿菜名去搜店」，等于把"爱吃肉"窄化成"卤肉饭"。现在改成三步：

1. **多菜 → 意图**：把今天想吃的整体（候选菜里最集中的菜系 + 今日想吃标签 + 你说的口语 + 最前面几道代表菜）翻成 **最多 6 个搜店关键词**，例如"想吃肉"会变成「川菜 / 烤肉 / 家常菜」这类品类词，而不是某个菜名；
2. **按意图搜一批店**：每个关键词走一次高德周边搜索，去重合并成一个候选店池；
3. **反查 + 打分**：反过来判断"每家店能做我们今天哪些候选菜"（按菜系和经营品类标签匹配，不依赖菜名），再按下面的维度给店排序。

**饭店评分维度（合计 100 分）**：距离 20、人均匹配 18、评分 16、菜系对口 14、**菜品覆盖 16（这家店能做几道你想吃的菜）**、**口味契合 10（经营品类 vs 你今天想吃的 + 长期口味画像，含"想吃肉"时看能做多少荤菜）**、用餐方式 6。

**人在环**：结果卡片下面会列出「附近这些店也能做你想吃的」，显示每家店的距离/评分/人均/**能做几道你想吃的**，
点一下就用这家店重新配一桌（会自动换成这家店能做的菜当主角，而不是硬套原来的主菜）。


| 数据源 | 需要 Key | 说明 |
| --- | --- | --- |
| 高德地图 | 需要（免费） | 真实店名、地址、电话、评分、人均、经纬度实算距离 |
| OpenStreetMap | 不需要 | 免 Key 兜底，但国内节点经常超时 |
| （已移除） | — | 原来有一份人工编的保定示例饭店库，已按需求整份删除：店名/人均是编的，公开后会误导人 |

**「我的」页面**（微信式底部 Tab）

头像档案摘要、忌口／过敏（11 项，硬性过滤）、口味偏好（12 项）、吃辣程度、默认预算档位、常用地址（一键填到首页）、AI 记忆（喜欢的／不喜欢的／最近吃过＋清空）、联网与模型设置、开发者视角。

- **换一批**：优先只从"还没出现过的店"里挑（整城轮完一轮就开新一轮、避开最近 6 家），主菜也会优先换新，
  所以点一次是真的换一家，不会原地打转；
- **不喜欢**：除了给口味标签记一笔（长期学习），还会把**这道菜和这家店硬屏蔽 24 小时**——
  否则只靠扣分经常压不住原来那道菜，用户会觉得"点了不喜欢还是它"。
  屏蔽内容在「我的 › AI 记忆 › 被屏蔽的推荐」里能看到，也能一键清空；
- 点「就吃这一桌」记的是喜欢，数据只存在本机浏览器。

**大模型接入**

大模型在两处参与，分工明确：**②b 负责"听懂"**（把「用一句话说说」里的口语翻译成标签和关键词，词表外的说法也能解析），**⑨ 负责"说话"**（把已经算好的一桌菜写成一段自然的推荐语）。**决策始终在本地算法手里**——选菜、过滤、打分、配桌、选店都是确定性计算，所以关掉大模型、没 Key 或调用失败时，功能一个不少，只是退回本地词表匹配、少一段推荐语。

支持 DeepSeek / OpenAI / 自定义 OpenAI 兼容接口，配了思考链显示和失败自动降级。口味解析的结果会缓存在本机（同一句话 7 天内不重复调模型），在「我的 › 清空联网缓存」里可以一并清掉。

## 智能体流水线

```
① 解析需求 → ② 读取长期记忆 → ③ 检索菜品库 → ④ 硬性规则过滤
→ ⑤ 9 维度打分 → ⑥ 联网检索真实饭店 → ⑦ 组合搭配（一桌菜）
→ ⑧ 按地址选饭店 → ⑨ 大模型润色
```

其中 ②b「大模型理解你说的话」是可选的一步（在第 ② 步之后）：解析成功就把标签并进"今日想吃"、关键词并进文本匹配；解析失败或大模型关闭，就直接走本地词表，用户无感。

打分维度：预算匹配、档位调性、今日想吃、口味画像、辣度适配、时段契合、新鲜感（7 天内吃过降权）、大众口碑、随机探索。

**商家数据库（自己采集的真实菜单）**

`data/shops.json` ＋ `商家数据库\` 文件夹构成一套"自采集"的菜单库：把菜单照片丢进文件夹 → `开发脚本\import-menu.mjs` 调 Windows 自带 OCR（带坐标）→ 大模型整理成结构 → `build-data.mjs` 写入 `data/shops.json` → 没见过的菜由 `gen-kb-records.mjs` 按词表规范补进上面那个菜品库。

它的定位只有一条：**把"这家店能不能做这道菜"从猜测换成事实，但绝不参与挑店**。推荐哪家店、给谁加分，仍然完全由高德搜回来的那批店按原来的规则算（距离/评分/菜系/人均…）。所以不会出现"想吃川菜却推沙县小吃"——川菜的锚定菜不在沙县的真实菜单里，它连候选都进不去。数据库里的店也必须先和高德搜到的店对上号（按店名匹配，忽略"（分店名）"）才会生效，是给高德的店补菜单，不是另立一派店铺。

页面优先 fetch `data/shops.json`（你改了立刻生效），fetch 不到（例如用 `file://` 直接打开本机文件）就用页面里由 `build-data.mjs` 自动写入的快照。结果卡上会标「📋 真实菜单 · 已采集 N 道」或「菜单未采集 · 按菜系推断」。

**两级作用范围（本店确认 / 品牌参照）**

一份菜单可以只对某一家分店生效，也可以给同品牌同名分店共用 —— 由 `data/shops.json` 里的 `scope` 决定：

| scope | 含义 | 怎么匹配 | 价格可信度 |
| --- | --- | --- | --- |
| `branch` **本店确认** | 在这一家分店实拍，用高德 POI ID 精确绑定 | 先是高德 ID 命中，其次完整店名（含分店名）一致 | 就是这家店的价格 |
| `brand` **品牌参照** | 同品牌同名分店共用 | 品牌名一致 **且同城**（跨城市不共享） | 参考价，各家可能不同 |

匹配优先级：`高德ID → 完整店名 → 品牌名+同城 → 品牌名是店名的一部分+同城`，都不中就回到菜系推断。绑定分店用 `开发脚本/bind-shop.mjs`，找店铺和高德 ID 用 `开发脚本/find-shop.mjs`。

实测依据：保定 3km 内 5 家沙县小吃，人均 ¥12 / ¥14 / ¥16 / ¥25 不等 —— 招牌菜（拌面、馄饨、蒸饺、炖罐）全国高度一致，可以品牌共用；价格差异明显，所以品牌参照的价格只能当参考。
- **标签体系**：3 档预算、3 大类、**40 个"今日想吃"标签（按类型分三套）**、11 项忌口（含食材映射）、12 个口味偏好
- **保定地理数据**：12 个商圈关键词、12 个地标坐标

## 技术说明

- 纯前端单文件，无框架、无构建、无外链资源，断网可用
- 距离用 haversine 按经纬度实算（联网时是真实直线距离）
- **搜店姿势**：以你的地址为中心做「周边搜索 + 关键词」并按距离排序、**翻页取 2～3 页（最多 24 家/每类菜）**。
  以前只取关键词搜索第 1 页再截断成 8 家——实测保定 3km 内其实有 75 家火锅店，而第 1 页里只有 7 家在 3km 内，
  所以会出现"搜火锅翻来覆去就那几家"。现在同样的地址能给出 24 家候选，主推 1 家 + 最多 3 家备选。
- 同一轮里多道菜共用关键词（比如一堆火锅菜都搜"火锅"）只会请求一次，省配额
- **请求量**：一次推荐通常只打 **2～4 个高德请求**（原来 11 个），点「换一批」基本 0～1 个；
  只给排前面的 4 个主菜搜店，关键词结果"够 12 家就不再翻页"
- **缓存**：搜过的关键词 / 周边 / 地理编码都缓存（搜索 10 分钟、地理编码 24 小时），
  换一批、不喜欢、来回点都不会重复请求；「我的 › 联网与模型设置」里有「清空联网缓存」可以强制刷新
- **配额可见**：设置页会显示"今天这台设备已用 N 次高德请求"，方便判断是不是把免费额度用完了
- **配额用完/Key 失效时**：会自动改用 OpenStreetMap 并在页面上说明原因，同时 10 分钟内不再打高德（避免反复失败）；
  ⚠️ 注意：公开链接里内置的是同一个 Key，**所有使用者共享这一份免费额度**；
  想彻底避免，可以让使用者填自己的 Key，或把公开版换成另一个 Key（设置页可随时替换）
- 高德支持浏览器跨域（实测 `CORS: *`、0.3 秒返回），所以不需要后端代理
- 数据来源在结果卡片上如实标注：高德实时数据 / OpenStreetMap 实时数据

## 后端（阿里云 FC）与账号

页面默认连朋友部署的函数计算后端（`DEFAULT_API_BASE`，可在「我的 › 后端与账号」里改或清空）：

| 接口 | 作用 |
| --- | --- |
| `POST /api/llm` | 大模型代理 —— DeepSeek Key 留在服务端，页面不再明文带 Key（需登录） |
| `POST /api/amap` | 高德代理 —— 高德 Key 同样留在服务端 |
| `POST /api/register` `POST /api/login` | 账号，服务端发 JWT，存本机 localStorage |
| `GET/PUT /api/profile` `GET/PUT /api/settings` | 口味、忌口、设置跨设备同步 |

**两条底线**（都有测试兜着，见 `开发脚本/test-server.mjs`）：

1. **后端挂了不影响用**：连不上、没登录、登录过期，一律回退成本机直连（用页面里内置的 Key）。
2. **后端 Key 不可用自动回退**：`/api/amap` 返回 Key 类错误（`10001`/`10002`/`10009`）时标记后端高德不可用，
   本次会话改用本机 Key 直连；其他异常（后端 502、格式不对）也静默回退，绝不把搜店搞崩。

**Agent 模式怎么保住**：工具调用准备了两种协议，`agentProtocol()` 自动选：

- `native` —— 直连 DeepSeek 时，`AGENT_TOOLS` 随请求发出，模型回 `tool_calls`；
- `text` —— 通道把 `tools` 吞掉时（早期那个后端代理就是这样：模型只能自己编 `<get_weather>` 文本），
  工具清单写进提示词，要求模型只回一行 `{"tool":"…","args":{…}}`，本地解析后还原成 `toolCalls`。
  **Agent 主循环两种协议共用**，所以"大模型主导决策"没有退化；代价是多一层文本信封，
  实测 7~8 步、7~8 秒能跑完（本机直连是 6~7 步、7~9 秒，基本持平）。

**协议结论是自动维护的**，用户不用管：

- 每次开跑 Agent 之前，`ensureAgentChannel()` 会在"没测过 / 超过 6 小时"时补一次探测
  （一个最小的 `ping_tool`，看模型回不回 `tool_calls`），把结论存进设置；
- 万一结论是错的（按原生跑，模型第一步没动静），`agentRun()` 会自动换成文字协议重跑一次，
  并把"这个通道吞 tools"记下来——用户视角只是"它自己换了条路"；
- 2026-09-23 后端那边把 `tools` 透传补上了：实测探测通过、Agent 走原生 function calling
  11.5 秒跑完（13 次工具调用），所以线上默认已经是原生协议。

「我的 › 后端与账号 › 跑一次后端自检」仍然可以手动测一遍：账号、大模型代理、高德代理 +
function calling 透传情况，结果会记住并显示在「工具协议」那一项上。

> 隐私：登录后口味画像与设置会存到后端（这是"跨设备同步"的前提）；不登录则一切只在本机。
